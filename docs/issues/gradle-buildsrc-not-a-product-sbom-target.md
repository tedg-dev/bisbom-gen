# Gradle `buildSrc` Is Not a Product SBOM Target

|            |                                                        |
| ---------- | ------------------------------------------------------ |
| Repo       | spring-boot (Gradle multi-module)                      |
| Component  | Java Phase 2 SBOM generation; `output_binaries` config |
| Status     | Resolved — build-logic JARs excluded generically       |
| Golden     | Removes `buildSrc_build` + `buildSrc_analyzed` baselines |

---

## Summary

The spring-boot analysis produced two SBOMs, `buildSrc_build.spdx.json`
and `buildSrc_analyzed.spdx.json`, for `buildSrc/build/libs/buildSrc.jar`.
`buildSrc.jar` is Gradle **build logic**, not a shipped Spring Boot
artifact, so it should never have been an SBOM target. It was swept in by
an over-broad `output_binaries` glob and baked into the golden baselines
by the legacy on-disk rescan. The fix is a generic build-logic-JAR filter
applied wherever `output_binaries` globs are expanded; the two `buildSrc`
golden files are removed as a deliberate baseline correction.

## What `buildSrc` Actually Is

`buildSrc/` is a directory name **reserved by Gradle**. Code placed there
is compiled automatically at the start of every build and put on the
classpath of the **build scripts themselves** — it holds custom plugins,
convention logic, and task definitions used to *build* the project.

Key properties:

- **Build-time only.** `buildSrc.jar` is consumed by Gradle to configure
  and run the build, then discarded. It is never compiled into, bundled
  with, or shipped inside any product artifact
  (`spring-boot-3.4.4.jar`, `spring-boot-configuration-processor-3.4.4.jar`).
- **Reserved convention.** Because Gradle special-cases the `buildSrc`
  directory name, its presence is an unambiguous, project-agnostic signal
  of build logic — not a heuristic.
- **Analogous to** a Maven build plugin or a Makefile helper: part of the
  build system, not the delivered software.

## How It Entered the SBOM Set

spring-boot's config uses a broad glob:

```yaml
spring-boot:
  output_binaries:
  - '**/build/libs/*.jar'
```

`**/build/libs/*.jar` matches every `build/libs/*.jar` on disk. Gradle
writes build logic to `buildSrc/build/libs/buildSrc.jar`, which the glob
matches alongside the real product JARs. The pipeline therefore treated
`buildSrc.jar` as just another output binary.

## The Provenance Question

The right question is not "is `buildSrc` a JAR we built?" (it is) but
"does it describe the provenance of the **shipped software**?"

We inspected the generated `buildSrc` SBOM: it contains **125 packages**,
all of which are build tooling — for example:

| Category            | Examples                                                        |
| ------------------- | --------------------------------------------------------------- |
| Gradle plugins      | `gradle-node-plugin`, `develocity-gradle-plugin`, `dokkatoo-plugin`, `spring-antora-plugin`, `spring-javaformat-gradle-plugin`, `nohttp-gradle` |
| Kotlin build stack  | `kotlin-stdlib`, `kotlin-reflect`, `kotlinx-coroutines-core`, `kotlinx-serialization-core` |
| Doc/lint tooling    | `dokka-core`, `checkstyle`, `nohttp-checkstyle`                  |

The content is **unique** (it is the build toolchain, distinct from the
product's runtime dependencies), but it describes the **build
environment**, not components that end up inside any Spring Boot artifact.

Conclusion: including it in the product SBOM conflates build-tooling
provenance with product provenance. If build-environment provenance is
ever wanted, it belongs in a separate build-environment SBOM (or an SPDX
`BUILD_TOOL_OF` relationship) — not as a product component SBOM. Per SBOM
best practice, a Bill of Materials documents the components of the shipped
software, so `buildSrc` must not be a product SBOM target.

## Why the Sidecar Cannot Capture It (and Should Not Have To)

Phase 1 sidecar interception recorded **zero** class events for
`buildSrc`. The `LD_PRELOAD` shim
(`libomnibor_java_intercept.so`) intercepts artifact writes in the main
build process, but Gradle compiles `buildSrc` during its **initialization
phase** through a separate mechanism whose process environment the shim
does not reach. Phase 2 then correctly reported:

```text
[ERROR] No treedb entry for buildSrc.jar — skipping SPDX generation
```

This is not a capture defect to chase: even if the sidecar were extended
to intercept the `buildSrc` compilation, the result would be an SBOM for
tooling that — per the provenance analysis above — should not be a product
SBOM in the first place. Capturing it would solve the wrong problem.

## Why the Golden Baselines Contained It

The golden files were generated by the **legacy on-disk rescan**, which
globs the filesystem for artifacts after the build. That rescan cannot
distinguish a product JAR from a build-tooling JAR, so it picked up
`buildSrc.jar` and emitted SBOMs for it. Golden files are **regression
baselines, not ground truth** — their purpose is to catch changes our code
introduces, not to assert that every entry is correct. The `buildSrc`
entries are a legacy over-inclusion, corrected deliberately here with a
reviewed golden diff.

## Decision

Exclude build-logic JARs from the product SBOM target set. This is the
industry-correct SBOM scope and is implemented generically — driven by the
reserved Gradle `buildSrc` convention, not by any repo-specific name check.

## Implementation

A single product-JAR predicate is applied at every site that expands
`output_binaries` globs, so all modes (standalone, sidecar) share one
definition of "product JAR".

`app/pipeline/binary_collector.py`:

- `_BUILD_LOGIC_DIRS = ("buildSrc",)` — reserved build-logic directories.
- `_is_build_logic_jar(path)` — true if any **ancestor directory** of the
  JAR is a reserved build-logic directory. Only ancestors are inspected,
  so the classification depends on the JAR's location, never its filename.
- `is_non_product_jar(path)` — combines the existing filename-based
  auxiliary-artifact rule (`-sources`, `-javadoc`, `-tests`,
  `original-`) with the new path-based build-logic rule.

Applied at:

| Site                                         | Role                                    |
| -------------------------------------------- | --------------------------------------- |
| `lang_runners.generate_java_adg_spdx`        | Java Phase 2 — emits `_build`/`_analyzed` SBOMs |
| `adg_spdx.AdgSpdxStep.generate`              | Standalone per-binary ADG SPDX          |
| `binary_collector.BinaryCollector.collect`   | Preserved-binary collection             |

## Verification

- `buildSrc` is no longer treated as a target; the
  `No treedb entry for buildSrc.jar` error is gone.
- spring-boot now emits SBOMs for exactly the two product JARs
  (`spring-boot-3.4.4`, `spring-boot-configuration-processor-3.4.4`),
  each file-level identical to golden.
- Unit tests cover `_is_build_logic_jar`, `is_non_product_jar`, and the
  glob-filter branch in both the collector and the ADG SPDX step.

## Golden File Impact

Two baselines are removed as a deliberate correction (product SBOMs
unchanged):

- `tests/golden/spdx/java/spring-boot/buildSrc_build.spdx.json`
- `tests/golden/spdx/java/spring-boot/buildSrc_analyzed.spdx.json`

Per project policy, golden files are only changed with explicit maintainer
approval; this removal was reviewed and approved as a baseline correction,
not a regression.
